# TalkArena 技术说明

## 1. 系统目标

TalkArena 的核心不是“做一个能聊天的 NPC”，而是做一个能在高压社交场景中持续施加反馈、识别状态、调整策略的训练系统。  
这决定了系统设计必须同时处理三件事：

- 用户说了什么
- 用户是怎么说的
- 多个 NPC 在当前局面下应该如何分工响应

因此项目采用了两条主线并行建设：

- 多模态链路：把文本、语音、表情统一成可计算的用户状态
- 多 Agent 链路：把场景、角色、策略、输出校验拆成职责清晰的协作模块

---

## 2. 整体架构

可以把系统看成一个闭环：

1. 前端采集用户输入
2. 本地语音识别与情绪分析
3. 多模态融合得到当前用户状态
4. 对话引擎根据状态驱动多角色生成
5. 本地语音合成 NPC 回复
6. 报告系统沉淀每轮训练结果

这不是简单的“输入一句话，返回一句话”。  
真正起作用的是中间的状态层：用户状态一旦被结构化，后面的 Agent、语音、报告都能围绕同一份状态工作。

---

## 3. 多模态部分的技术亮点

### 3.1 统一情绪状态，而不是分散打分

多模态核心在 `G:\GitHub\TalkArena\core\multimodal_analyzer.py`。  
这里不是把“表情分数、语音分数、文本分数”各自独立展示，而是通过 `MultimodalFusionEngine` 汇总为统一的 `MultimodalEmotionState`。

这样做的价值很直接：

- NPC 决策看到的是“当前人处于什么状态”，不是三份互不相干的原始信号
- 前端展示、局后报告、策略切换共用一套状态定义
- 后续替换模型时，只需要替换某个模态的提取器，不需要重写全链路

系统目前保留的核心状态包括：

- `primary_emotion`：主情绪
- `emotion_intensity`：情绪强度
- `confidence`：判定置信度
- `hidden_sentiment`：表层表达之外的潜在倾向
- `inconsistencies`：跨模态不一致信号

其中最有训练价值的不是“开心/难过”这种浅层标签，而是 `inconsistencies`。  
在真实社交场景里，很多失误并不出在内容本身，而是“嘴上说没事，声音已经虚了；话很客气，但表情和节奏已经顶上去了”。系统把这种冲突显式保留下来，后续 NPC 才能做出更像真人的追问、施压或安抚。

### 3.2 语音不只做转写，还做状态估计

本地 STT 服务在 `G:\GitHub\TalkArena\core\stt_local.py`，识别引擎使用 Vosk。  
这条链路的关键不是“把音频转成文字”，而是同时产出声学特征，再交给 `VoiceEmotionAnalyzer`。

目前使用的特征包括：

- `loudness`：响度
- `speech_rate`：语速
- `energy_variance`：能量波动

在 `G:\GitHub\TalkArena\core\multimodal_analyzer.py` 中，这些特征进一步被映射到：

- `happy`
- `sad`
- `angry`
- `nervous`
- `confident`
- `hesitant`

并继续压缩为三条更稳定的连续轴：

- `valence`
- `arousal`
- `dominance`

这个设计的亮点在于：  
离散情绪标签适合展示，连续维度适合决策。  
例如“紧张”和“愤怒”都可能有较高 arousal，但 dominance 不同；系统可以据此区分“需要继续施压”还是“应该收一收火候”。

### 3.3 多模态融合是连续过程，不是一次性判断

`MultimodalFusionEngine` 不是纯函数，它内部挂了：

- `UserEmotionStateMachine`
- `EmotionMemory`

这意味着系统看的不是某一帧、某一句，而是情绪轨迹。  
对于训练产品，这一点比单次识别准确率更重要。

具体价值有三点：

- 可以判断用户是在稳定下来，还是越说越乱
- 可以把“短时失误”和“持续性失控”区分开
- 可以让 NPC 的策略切换基于趋势，而不是基于瞬时噪声

这也是为什么报告页里适合展示“综合点评”和“下一轮提升点”，而不只是静态分数。

### 3.4 文本情绪只做轻量补偿，不抢主导权

当前文本分析采用轻量规则法，作为低成本补偿信号。  
原因很明确：

- 文本最容易拿到，但最容易“被修饰”
- 社交训练里，用户文字往往不是最真实的状态来源
- 语音和表情更接近即时反应，适合承担主导信号

这个取舍比较务实。  
它承认文本情绪分析有价值，但不让文本把整个多模态链路带偏。

## 4. 多 Agent 部分的技术亮点

### 4.1 不把“多角色”做成多段模板，而是做成统一编排

运行时入口在 `G:\GitHub\TalkArena\core\engine.py`。  
`TalkArenaEngine` 同时持有多种能力组件：

- `UnifiedAgent`
- `MultiAgentOrchestrator`
- `RAGEngine`
- `DecisionEngine`
- `OutputValidator`

当前主路径默认走 `UnifiedAgent`。这不是削弱多 Agent，而是把多角色协作放到一个统一上下文里执行，避免多个 Agent 各说各话、节奏失真。

它的实际收益是：

- 多个 NPC 能共享同一场景进度
- 每个角色保持自己的身份和说话风格
- 发言顺序、插话节奏、停顿时间可以统一调度

这比“分别问三个 Agent 再拼起来”更稳，因为后者最容易出现角色间重复、冲突、抢话和状态不一致。

### 4.2 角色协作的最小单位是 utterance 队列

系统不是一次返回一大段合并文本，而是返回 `utterances` 队列。  
每个元素至少包含：

- `npc_id`
- `text`
- `delay_ms`

这套设计非常关键，原因有三点：

- 前端可以按角色逐条展示，形成真实的多人对话感
- 可以中途打断、继续、插入用户发言
- 可以把语音合成、头像状态、打字机效果和同一条 utterance 绑定

也就是说，多 Agent 的价值不只是“有多个名字在说话”，而是系统真正具备了多人轮转的时序结构。

相关前端编排在 `G:\GitHub\TalkArena\main.py`：

- `displayUtterances()`
- `continueNPC()`
- `interrupt()`
- `speakNPC()`

这一层把智能体输出和最终用户感知连接了起来。

### 4.3 决策、知识、校验分层，避免一个 Agent 包打天下

`TalkArenaEngine` 里保留了明确的职责分层：

- `DecisionEngine`：判断当前该采取什么对话策略
- `RAGEngine`：补充场景知识和上下文
- `OutputValidator`：校验输出质量和角色一致性

这种分层的好处不是“模块多”，而是每一层都能单独强化：

- 想提升策略性，改 `DecisionEngine`
- 想提升场景真实感，改 `RAGEngine`
- 想降低跑题和人设崩坏，改 `OutputValidator`

这比把所有责任都压到一个 prompt 上更工程化，也更适合持续迭代。

### 4.4 多 Agent 的重点是“关系”，不是“数量”

TalkArena 的场景本质上是高压互动，不是问答。  
所以多 Agent 真正重要的是角色关系：

- 谁负责施压
- 谁负责缓和
- 谁负责观察和补刀
- 谁在什么时候沉默

这一点在社交训练场景里尤其重要。  
真实饭局、面试、群体冲突里，压力从来不是单点产生的，而是由多人互动共同形成。系统采用多角色编排，就是为了让这种“复合压力”能被模拟出来。

## 5. 本地语音链路设计

### 5.1 本地 STT：识别和情绪共用一份音频

前端录音后，把音频送到 `POST /api/stt`。  
后端在 `G:\GitHub\TalkArena\core\stt_local.py` 中完成：

- 音频读取
- 重采样到 16k
- 转成 PCM16
- Vosk 离线识别
- 声学特征提取

这里一个很实际的工程点是：  
STT 和语音情绪分析共用同一份音频，不重复采集、不重复建链路。  
这样延迟、资源占用和调试复杂度都明显更低。

### 5.2 本地 TTS：让 NPC 的“说法”具备表演性

本地 TTS 服务在 `G:\GitHub\TalkArena\core\tts_local.py`，当前选型是 StyleTTS2。  
选择它的原因不是单纯追求音质，而是它更适合承担“情绪化发声”的角色。

在训练系统里，TTS 如果只做到“念字清楚”，体验仍然是平的。  
真正有效的是：

- 用户听得出角色态度
- 语气和台词一致
- 同一句话在不同情绪下能有不同压迫感

当前链路支持把情感参数传入 TTS，再由前端按 utterance 顺序播放。  
这使得 NPC 的输出从“文本反馈”升级成“带态度的反馈”。

### 5.3 语音链路全部本地化，目的不是离线本身，而是可控

本地化带来的核心价值有三点：

- 可部署：不依赖浏览器 Web Speech，也不绑定外部云 API
- 可调参：STT/TTS 都可以按项目目标做针对性优化
- 可扩展：后续加入说话人风格、场景音色、情绪强度控制更容易

对训练类产品来说，这种可控性比“临时能跑起来”更重要。

## 6. 前端交互层为什么重要

很多项目把前端当成展示壳，但 TalkArena 的前端其实承担了“对话导演”的职责。

在 `G:\GitHub\TalkArena\main.py` 里，前端至少完成了几件关键事情：

- 录音、提交、识别结果回填
- 按 utterance 队列逐条展示 NPC 发言
- 角色头像状态切换
- 本地音频顺序播放
- 支持打断 NPC、继续 NPC
- 保存并展示历史报告

这意味着用户看到的“代入感”，并不只来自模型能力，还来自前端把多角色时序、语音和视觉反应组织成一个连续过程。

如果没有这一层，后端再强，最终也只会变成普通聊天框。

---

## 7. 局后报告为什么是系统的一部分

报告页不是附属页面，而是训练闭环的一部分。

当前报告至少沉淀了三类信息：

- 量化分数
- 综合点评
- NPC 侧内心反馈

这三类信息分别对应三种用途：

- 分数：帮助用户快速定位结果
- 点评：解释为什么会这样
- NPC 内心反馈：把“别人怎么感受到你”显式化

社交训练里，用户最缺的通常不是建议，而是反馈视角。  
NPC 内心 OS 的价值就在这里：它把隐性的社交后果翻译成可见文本，便于用户建立“表达 -> 感知 -> 结果”的因果链。

## 8. 当前方案的工程取舍

### 8.1 为什么 STT 选 Vosk

因为当前目标优先级是：

- 本地可跑
- 链路稳定
- 资源要求可接受

Vosk 不一定是识别效果最强的，但作为本地 STT 基础设施足够稳定，适合先把全链路打通。

### 8.2 为什么 TTS 选 StyleTTS2

因为 TalkArena 不只是工具型播报，而是角色型播报。  
用户需要听见情绪、态度和压迫感，这决定了 TTS 必须优先考虑表达力，而不只是吞吐量。

### 8.3 为什么保留统一 Agent 主路径

因为多人对话场景里，一致性比“绝对自治”更重要。  
系统优先保证：

- 场景一致
- 角色一致
- 节奏一致

在这个基础上，再逐步加强不同角色的独立策略空间。

---

## 9. 后续最值得继续加强的方向

如果继续往下做，最有价值的不是再堆模块，而是把下面三点做深：

- 更强的跨模态冲突检测：例如“文本客气但声音明显抗拒”
- 更细的角色策略分工：把施压者、观察者、缓冲者的策略显式化
- 更稳定的情绪化语音映射：让 TTS 情感强度和当前场景压力等级联动

这三点一旦做实，TalkArena 的差异化会很明确：  
它不是一个“会说话的 NPC 应用”，而是一个“能识别状态、组织多人压力、并把反馈闭环到训练结果里”的社交训练系统。
